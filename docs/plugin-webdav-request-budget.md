# Бюджет запросов WebDAV для фонового плагина

`withWebDavRequestBudget(origin, action)` временно объединяет запросы файлов
плагина и запросы WebDAV-синхронизации хоста в одну очередь на каждый origin.
Origin — это схема, имя сервера и порт, например `https://files.example`.
Новый API доступен в `plugin.js` на Windows и в браузере. Перед вызовом проверьте
его наличие. Обычная сборка без этого API не обеспечивает данный бюджет.

Плагин должен объявить `permissions: ["http"]` и нужное имя сервера в
`allowedHosts`. Хост проверяет разрешение и точное имя сервера. Как и
`PluginAPI.request`, API блокирует приватные и служебные адреса. Origin не должен
содержать путь, параметры, фрагмент, имя пользователя или пароль.

## Порядок работы

1. Плагин открывает scope вызовом API и передаёт асинхронный callback `action`.
2. Хост передаёт callback собственный `budgetFetch` с обычными типами `fetch` и
   `Response`. Он допускает только заданный origin и запрещает редиректы.
3. Плагин использует этот fetch для файлов. Запросы обычных WebDAV- и
   Nextcloud-провайдеров проходят через тот же ограничитель. Если сервер файлов
   и сервер синхронизации различаются, у каждого будет отдельная очередь.
4. Хост снимает scope после фактического завершения callback, включая ошибку.

```text
plugin.js → withWebDavRequestBudget → общий бюджет на origin → HTTP
                 │                       ↑
                 └→ budgetFetch ──────────┤
WebDAV / Nextcloud sync → APP_WEBDAV_FETCH ┘
```

Ограничитель допускает два запроса сразу. Затем он добавляет один токен за шесть
секунд. Токен разрешает начало одного запроса. Длительное ожидание или приостановка
приложения не накапливают больше двух токенов. История токенов сохраняется между
scope. Несколько одновременных scope используют общий бюджет.

Пока callback выполняется, ограничитель также задерживает обычную
WebDAV-синхронизацию. Это необходимо, поскольку обычная синхронизация и сетевые
операции хоста также отправляют HTTP-запросы. Между операциями плагина
обычная синхронизация работает без этой задержки. Dropbox, OneDrive и SuperSync
не используют новый fetch и сохраняют прежнее поведение.

## Пример

```javascript
if (typeof PluginAPI.withWebDavRequestBudget !== 'function') {
  throw new Error('Для этой операции нужен API бюджета WebDAV');
}

const bytes = await PluginAPI.withWebDavRequestBudget(
  'https://files.example',
  async (budgetFetch) => {
    const response = await budgetFetch('https://files.example/attachments/file.pdf');
    if (!response.ok) throw new Error('Файл не получен');
    return await response.arrayBuffer();
  },
);
```

Тело ответа нужно прочитать внутри callback. Не сохраняйте `budgetFetch` для
последующих операций. После завершения scope хост отзывает этот fetch и отменяет
его незавершённые запросы. Отдельные `RequestInit.signal` поддерживаются.

## Ошибки и выгрузка

Ответ 429 или 503 возвращается вызывающему коду один раз. Ограничитель не повторяет
GET, PUT или DELETE. Последующие запросы к тому же origin сразу завершаются ошибкой
до истечения `Retry-After`. Поддерживаются целое число секунд и HTTP-date. Если
заголовок отсутствует или некорректен, пауза составляет минуту. Пауза сохраняется
после завершения scope, чтобы обычная синхронизация не продолжила запросы сразу
после ограничения сервера.

HTTP-date читается как GMT, включая прежние формы RFC850 и asctime. Форматы
определены в [RFC 9110, §5.6.7 и §10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-5.6.7).

Выгрузка плагина запрещает новые вызовы старого экземпляра API и отменяет его raw
fetch. Она не подменяет завершение уже выполняемой синхронизации хоста. Scope остаётся
активным до фактического завершения callback. Плагин должен завершать свои операции.
Если операция требует продолжения после сбоя, плагин сам сохраняет намерение до
сети. API не делает DELETE безопасным и не заменяет проверку синхронизации,
владельца файла и журнала операций.

## Границы поддержки

- API работает только в фоновом `plugin.js`. Iframe не передаёт callback через
  bridge; его UI должен отправить сообщение собственному фоновому плагину.
- Native HTTP на Android и iOS использует другой транспорт. На этих платформах
  вызов отклоняется до запуска callback. Windows и браузер используют fetch.
- Очередь локальна одному экземпляру приложения. Она не координирует другие
  компьютеры, вкладки и приложения. Общий лимит IP-адреса не гарантируется.
- Браузер может дополнительно отправить CORS OPTIONS. Эти запросы создаёт сам
  браузер, и они не расходуют токены очереди. Серверный лимит должен учитывать их.
- Два стартовых токена и пополнение одного токена за шесть секунд задают локальную
  политику API. Эти параметры не гарантируют соблюдение серверной квоты для общего
  IP-адреса.
- Бюджет не меняет CAS, проверку целостности, форматы файлов и sync-схему.

Реализация находится в `src/app/op-log/sync-providers/platform/`. Регрессионные
тесты проверяют очередь и реальные app factory WebDAV/Nextcloud с перехваченным
fetch, а также общий путь raw-запросов, отмену и отсутствие задержки вне scope.
